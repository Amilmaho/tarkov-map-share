# 系统架构

## 1. 目标与范围

`tarkov-map-share` 的目标是让 2–5 名队友在同一张地图上看到彼此的位置、标记与路线。

范围内的能力：

* 房间的创建、加入、退出与状态恢复。
* 玩家位置、朝向、地图选择的实时同步。
* 标记（点位 / 图标 / 文字）与路线的增删改查。
* 地图图片加载、缩放平移、坐标换算与校准。

范围外的能力：

* 读取游戏内存、注入进程、模拟输入。
* 战绩、物品、任务数据查询（后续可做只读集成）。
* 任何形式的自动化对局操作。

## 2. 系统总览

## 3. 模块划分

### 3.1 桌面端 `apps/desktop`

* **Main 进程**：窗口与生命周期、托盘、系统通知、本地配置与 Token 的安全存储、自定义协议的素材加载。
* **Preload**：通过 `contextBridge` 暴露最小化、白名单化的 IPC API；渲染进程不开启 `nodeIntegration`。
* **Renderer**：React 应用，按功能分层：
  * `features/map`：地图视图、图层、缩放平移交互。
  * `features/room`：房间创建/加入、成员列表。
  * `features/markers`：标记与路线的增删改查。
  * `features/session`：连接状态、重连、离线队列。
  * `stores`：Zustand Store，按领域拆分。
  * `services/ws`：WebSocket 客户端（连接、心跳、重连、消息分发）。

### 3.2 服务端 `apps/server`

* **gateway**：连接建立、鉴权、心跳、消息入口与 Zod 校验。
* **rooms**：房间注册表、成员、状态快照、广播。
* **handlers**：按消息类型划分的处理函数，纯逻辑与传输层分离，便于测试。
* **persistence**：SQLite 读写，仅在房间结束或周期性快照时落盘。

### 3.3 共享层 `packages/shared`

* `protocol`：消息类型、版本号、Zod Schema、错误码。
* `model`：跨端实体类型（Room、Marker、PlayerState…）。
* `map`：坐标变换、校准数据解析、边界与精度工具。
* `utils`：ID 生成、时间、日志等无副作用工具。

## 4. 关键数据流

### 4.1 位置同步

```text
用户移动 / 手动输入坐标
   → 桌面端 Store 更新（乐观）
   → ws 客户端发送 player.update（限流，默认 10Hz）
   → 服务端校验并更新房间状态
   → 广播 player.updated 给房间内其他成员
   → 其他客户端更新 Store 并重绘地图
```

服务端对同一玩家的位置更新做**节流 + 合并**，只广播最新状态，避免高频抖动。

### 4.2 标记与路线

标记使用**客户端生成 ID + 服务端确认**的方式，保证乐观更新时不会出现重复点。
删除采用软删除（`deletedAt`），避免并发场景下"删了又被旧快照加回来"。

### 4.3 加入房间与状态恢复

```text
客户端 room.join
   → 服务端校验房间码与容量
   → 返回 room.joined（含自己信息）
   → 紧接着推送 room.snapshot（成员、地图、标记、路线）
   → 客户端以快照覆盖本地状态，之后按增量消息更新
```

### 4.4 位置采集：截图文件名

```text
游戏内按截图键（Windows 主机）
   → 截图落入 %USERPROFILE%\Documents\Escape from Tarkov\Screenshots
   → 桌面端监听目录，仅对新文件解析文件名
   → 得到 position(x, y, z) 与 heading（四元数换算）
   → player.update（source: "screenshot"）
   → 服务端权威状态 → 广播给房间内其他成员
```

要点：

* 只读文件，不读取图片内容；启动时先做一次目录快照，避免历史截图被批量上报。
* 解析失败或目录不存在时静默降级到地图点选通道。
* 桌面端因此**首发目标平台为 Windows**（游戏所在机器）。

## 5. 技术选型

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 桌面壳 | Electron | 跨平台、生态成熟、Canvas 性能足够 |
| 渲染 | React + Canvas 2D | 图层简单、可控、避免地图库体积 |
| 状态 | Zustand | 轻量、易测试、适合高频更新 |
| 传输 | 原生 `ws` + 自定义协议 | 协议显式可控、便于文档化与测试 |
| 校验 | Zod | 类型与运行时校验同源 |
| 存储 | SQLite | 单机部署简单，够用 |
| 测试 | Vitest + Playwright | 单元/集成快，端到端覆盖桌面端 |

## 6. 信任模型与限制

* 房间是**互信小队**场景，服务端不做反作弊级的位置校验。
* 服务端仍然承担：消息格式校验、容量限制、频率限制、越权访问拦截。
* 房间码是**准入门槛**而非强认证；后续可加入口令或一次性邀请链接。
* 单房间成员上限默认 5 人（可配置），超出直接拒绝。

## 7. 部署

| 场景 | 方式 |
| --- | --- |
| **房主模式（默认）** | 服务端作为库嵌入房主的客户端进程，监听 `0.0.0.0:8787`；同 WiFi 的队友直接连 `ws://<内网IP>:8787`，跨网络先接入 Tailscale 之类的虚拟局域网 |
| 单机模式 | 只监听 `127.0.0.1`，队友不可见，等价于"自己是房主且没有队友" |
| 公网联机 | VPS 运行同一份服务端（`npm run start`），前置 Nginx/Caddy 处理 TLS，客户端用 `wss://` |

服务端要求：`createGameServer()` 返回的句柄可在同进程内 `close()`；
独立部署时是无状态进程 + 本地 SQLite 文件，可直接用 `systemd` / `pm2` 托管。

房主模式的取舍：

* 队友之间不依赖任何第三方服务器，零成本、低延迟。
* 房主退出 = 服务端进程结束 = 房间消失（客户端重连失败后提示"房主已关闭房间"）。
* 房主的上传带宽决定队友的同步质量，房主掉线会导致整队同步中断。

## 8. 演进方向

1. 房间快照持久化与"恢复上次队伍"。
2. 只读集成 tarkov.dev 地图与物品数据（需遵守其许可与速率限制）。
3. WebRTC DataChannel 直连，降低对中心服务器的依赖。
4. 只读的游戏日志解析（仅限官方允许的日志文件），用于自动填充地图名与角色名。
