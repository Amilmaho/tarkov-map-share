# 架构决策记录（ADR）

格式：背景 → 决策 → 理由 → 后果。状态分为 `已接受` / `待定` / `已废弃`。

---

## ADR-0001 Monorepo + npm workspaces

**背景**：桌面端、服务端、共享类型必须保持同步，分别建仓会导致类型漂移。

**决策**：使用单个仓库，npm workspaces 管理 `apps/*` 与 `packages/*`。

**理由**：一次 `npm install` 完成依赖；共享层改动可被两端立即感知；CI 配置简单。

**后果**：仓库体积增大；需要约定"共享层不依赖业务层"的方向性约束。

**状态**：已接受

---

## ADR-0002 桌面端选型 Electron + React + TypeScript

**背景**：需要跨平台、能常驻、能画高性能地图，并且开发速度快。

**决策**：Electron + React + TypeScript + Vite，地图用 Canvas 2D 自绘。

**理由**：生态成熟；Canvas 完全可控，避免地图库的额外体积与坐标抽象冲突；
渲染进程与主进程隔离，便于做安全边界。

**后果**：安装包偏大（约 100MB+）；需要严格配置 `contextIsolation` 与 IPC 白名单。

**状态**：已接受

---

## ADR-0003 使用原生 `ws` + 自定义协议

**背景**：实时同步的协议需要被文档化、可测试、可演进。

**决策**：服务端使用 `ws`，自定义版本化消息信封（见 `WEBSOCKET_PROTOCOL.md`）。

**理由**：消息完全显式，便于写 Schema 测试与协议文档；不引入额外抽象层。

**后果**：房间、重连、心跳需要自己实现，但逻辑量可控且更易测试。

**备选**：Socket.IO（被否决：协议隐式、体积更大、与文档化目标冲突）。

**状态**：已接受

---

## ADR-0004 以 Zod Schema 作为类型与运行时校验的单一事实来源

**背景**：网络输入不可信，且类型定义容易与校验逻辑分叉。

**决策**：在 `packages/shared` 用 Zod 定义 Schema，类型由 `z.infer` 推导。

**理由**：一份定义同时服务编译期类型与运行期校验，减少重复与漂移。

**后果**：共享层成为两端共同依赖，需要谨慎控制其体积与依赖数量。

**状态**：已接受

---

## ADR-0005 服务端权威的房间状态

**背景**：多人并发修改标记时，纯客户端同步会产生冲突与重复。

**决策**：服务端保存权威状态；客户端可乐观更新，最终以 `ack` / 广播为准。

**理由**：冲突处理集中在一处；重连后可用快照一键追平。

**后果**：服务端承担更多逻辑与测试成本；需要明确定义 last-write-wins 与软删除规则。

**状态**：已接受

---

## ADR-0006 内存态 + SQLite 持久化

**背景**：在线房间需要低延迟读写；同时希望重启后不丢全部数据。

**决策**：在线状态放内存，房间/标记/路线周期性或按事件落 SQLite。

**理由**：单机部署零依赖，读写性能足够；避免过早引入数据库服务。

**后果**：进程崩溃可能丢失最近几秒的数据；多实例水平扩展受限。

**状态**：已接受

---

## ADR-0007 地图坐标使用 4 点单应变换

**背景**：地图图片与游戏世界坐标之间存在平移、缩放、旋转与轻微透视差异。

**决策**：默认使用 4 点单应变换，3 点仿射作为退化方案。

**理由**：精度更高，能覆盖旋转与透视；控制点数据可人工校准并可回归测试。

**后果**：需要为每张地图维护校准数据；控制点选择质量直接决定精度。

**状态**：已接受

---

## ADR-0008 状态管理使用 Zustand

**背景**：位置更新频率高（约 10Hz），需要轻量、可测试的状态方案。

**决策**：按领域拆分 Zustand Store（session / room / map / markers）。

**理由**：无 Provider 嵌套、选择器粒度细、易于单测。

**备选**：Redux Toolkit（被否决：模板代码多，对高频更新不友好）。

**状态**：已接受

---

## ADR-0009 测试体系 Vitest + Playwright

**背景**：坐标与协议逻辑需要快速单测，桌面端需要端到端验证。

**决策**：Vite 生态统一使用 Vitest；桌面端主流程用 Playwright 驱动 Electron。

**理由**：配置与构建工具一致；两种测试共享类型与测试数据。

**后果**：CI 需要能启动 Electron（Linux 下需要 `xvfb`）。

**状态**：已接受

---

## ADR-0010 明确禁止任何游戏进程交互

**背景**：塔科夫有反作弊系统，涉及内存读取/注入的工具既有封号风险也有法律风险。

**决策**：项目只处理玩家主动提供的数据，绝不读取游戏内存、注入进程或模拟输入。

**理由**：保证工具合规、可持续；把产品价值定义在"协作共享"而非"自动获取信息"。

**后果**：位置等数据需要人工输入或官方允许的日志解析；产品体验需要在易用性上补足。

**状态**：已接受

## ADR-0011 以游戏截图文件名作为位置采集主通道

**背景**：塔科夫不显示坐标，也没有官方 API。实测发现游戏内置截图（玩家按键触发）会把
玩家位置 `(x, y, z)` 与旋转四元数 `(x, y, z, w)` 写入文件名，属于官方自身产生的数据。

**决策**：把「监听截图目录 → 解析文件名」作为位置采集的主通道，地图点选与手动输入作为兜底。

**理由**：

* 拿到的是游戏原生精确坐标，精度远高于肉眼点选（±10–30 米）。
* 玩家动作从「在地图上找自己」简化为「按一下截图键」，不打断战斗。
* 只读文件名，不触碰游戏进程、不读图片内容，与 ADR-0010 的红线不冲突。

**后果**：

* 桌面端**首发平台为 Windows**：游戏与截图目录都在 Windows 主机上，macOS 仅用于开发调试。
* 需要目录监听、去重（文件名时间只到分钟）、连拍节流与解析失败的降级逻辑。
* 解析器必须集中在 `packages/shared/src/capture`，并随游戏版本变化保持可回归测试。
* 文件名不含地图名，需要额外的地图归属来源（日志解析或手动选择）。

**备选**：读取游戏日志（被降级为辅助：用于判断当前 Raid 的地图与局内状态）。

**状态**：已接受

## ADR-0012 当前 Raid 的地图由玩家手动选择

**背景**：截图文件名只包含坐标，不含地图信息（见 ADR-T5）。可选方案是解析游戏日志自动识别
当前 Raid 的地图，或由玩家在客户端手动选择。

**决策**：MVP 阶段由玩家在客户端手动选择地图；日志解析不实现。

**理由**：

* 手动选图是零成本的（进图时选一次），且不依赖日志格式的稳定性。
* 日志解析需要额外的文件监听、格式适配与版本回归，收益仅省下一次点击。
* 手动选择让"换图"变成显式操作，正好与 `map.changed` 的房间级同步语义吻合。

**后果**：

* 玩家忘记选图时，坐标会被解释到错误的地图上；需要在界面上明确显示当前地图。
* 后续若要做自动识别，只需替换地图来源，不影响坐标与协议层。

**状态**：已接受
