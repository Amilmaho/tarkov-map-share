# 地图坐标系统

本文件定义**游戏世界坐标**、**地图图像坐标**与**屏幕坐标**之间的关系。所有换算实现集中在
`packages/shared/src/map`，禁止在 UI 组件里重复实现。

---

## 1. 三套坐标系

| 坐标系 | 单位 | 原点 | 说明 |
| --- | --- | --- | --- |
| 世界坐标 `world` | 米 | 游戏世界原点 | `{ x, y, z }`，`y` 为高度 |
| 图像坐标 `image` | 像素 | 地图图片左上角 | `{ px, py }`，`py` 向下增长 |
| 屏幕坐标 `screen` | CSS 像素 | 画布左上角 | `{ sx, sy }`，由视图变换得到 |

范围只关心 **XZ 平面**：`y`（高度）不参与地图定位，只作为信息展示。

## 2. 世界坐标约定

* 单位：米。
* **X 轴**：向东为正。
* **Z 轴**：向北为正。
* **Y 轴**：向上为正（高度）。
* **朝向 `rotation`**：偏航角，单位为度，`0°` 指向正北（`+Z`），顺时针为正，
  取值范围 `[0, 360)`。

> 约定必须在客户端一致使用；如需与第三方数据源（如 tarkov.dev）对接，在适配层转换，
> 不允许把第三方约定泄漏到业务代码。

## 3. 地图图像与校准

每张地图对应一份校准数据：

```jsonc
// maps/customs/calibration.json
{
  "mapId": "customs",
  "image": {
    "src": "assets/maps/customs.png",
    "width": 4096,
    "height": 4096
  },
  "rotation": 0,             // 地图图片相对世界坐标的旋转角（度）
  "controlPoints": [
    { "world": { "x": -180.0, "z": 240.0 }, "image": { "px": 812.0, "py": 1150.0 }, "label": "控制点 A" },
    { "world": { "x": 300.0,  "z": 200.0 }, "image": { "px": 3310.0, "py": 990.0 },  "label": "控制点 B" },
    { "world": { "x": 260.0,  "z": -260.0 }, "image": { "px": 3480.0, "py": 3020.0 }, "label": "控制点 C" },
    { "world": { "x": -150.0, "z": -220.0 }, "image": { "px": 700.0, "py": 3180.0 },  "label": "控制点 D" }
  ],
  "source": {
    "name": "待填充的社区地图来源",
    "url": "",
    "license": "待确认"
  }
}
```

> 上表中的世界坐标与像素值均为**示例占位**，必须通过实际校准流程替换。

## 4. 坐标变换

### 4.1 仿射变换（3 点）

当图片没有透视畸变时，使用仿射变换即可：

```text
[px]   [a  b] [x]   [tx]
[py] = [c  d] [z] + [ty]
```

由 3 个不共线的控制点解出 `a b c d tx ty`。

### 4.2 单应变换（4 点，推荐）

地图图片与游戏世界之间通常存在轻微透视/旋转差异，因此**默认使用 4 点单应
（homography）变换**，把世界坐标投影到图像坐标：

```text
        h00 * x + h01 * z + h02
px = ─────────────────────────────
        h20 * x + h21 * z + 1

        h10 * x + h11 * z + h12
py = ─────────────────────────────
        h20 * x + h21 * z + 1
```

实现要求：

1. 用 4 个控制点求解 8 个未知量（DLT，`H33` 归一化为 1）。
2. 控制点退化（三点共线、点重复）时直接报错并提示重新校准。
3. 提供 `invert()`，用于图像坐标反算世界坐标（点击地图取坐标）。
4. 剩余误差（reprojection error）> 3 像素时输出警告。

### 4.3 屏幕变换

视图状态：

```ts
type Viewport = {
  scale: number;   // 1 = 100% 图像像素 : CSS 像素
  offsetX: number; // 图像左上角在画布中的位置
  offsetY: number;
};
```

```text
sx = px * scale + offsetX
sy = py * scale + offsetY
```

缩放时以鼠标位置为锚点：

```text
offset' = cursor - (cursor - offset) * (scale' / scale)
```

## 5. 校准流程

1. 在地图上选取 **4 个易于辨认**的地标（如撤离点、标志性建筑角）。
2. 用游戏内坐标（或可信任的公开数据）记录每个地标的世界坐标 `{ x, z }`。
3. 在地图图片上读取对应像素坐标 `{ px, py }`，写入 `calibration.json`。
4. 运行校准校验脚本，输出 8 个点之外的验证点误差。
5. 误差 ≤ 2 像素视为合格；2–5 像素需说明原因；> 5 像素重新选点。

验证脚本（规划中）：

```bash
npm run map:verify -- --map customs
```

## 6. 精度与边界情况

| 情况 | 处理 |
| --- | --- |
| 坐标超出图片边界 | 允许绘制，但标记为"越界"样式并提示 |
| 地图图片被旋转 | 在 `rotation` 中声明，或直接在校准点中体现，不要混用两种方式 |
| 高度 `y` | 不参与定位；仅在悬浮提示中显示 |
| 坐标精度 | 世界坐标保留 2 位小数，像素坐标保留 1 位小数 |
| 大缩放倍数 | 缩放范围限制在 `0.2x ~ 8x`，避免浮点漂移与纹理模糊 |
| 多显示器 DPI | 屏幕坐标使用 CSS 像素，绘制时按 `devicePixelRatio` 放大画布后备缓冲 |

## 7. 位置采集通道：游戏截图文件名

塔科夫的内置截图（玩家按键触发）会把玩家位置与朝向写进**文件名**，这是本项目的主要位置来源。
解析实现固定在 `packages/shared/src/capture/screenshot-filename.ts`，禁止在别处重复实现。

真实样本（Windows 主机，手动按键截图）：

```text
2026-09-18[20-06]_-323.69, 2.44, -225.63_0.02332, 0.54903, -0.01533, 0.83534_15.72 (0).png
```

| 片段 | 含义 | 备注 |
| --- | --- | --- |
| `2026-09-18[20-06]` | 日期 + 本地时间 | 只精确到分钟；同一分钟多张靠序号区分 |
| `-323.69, 2.44, -225.63` | 世界坐标 `x, y, z` | 单位米；`y` 为高度，与第 2 节约定一致 |
| `0.02332, 0.54903, -0.01533, 0.83534` | 旋转四元数 `x, y, z, w` | 单位四元数（实测模长 1.000003） |
| `15.72` | 待定 | 候选：游戏内时间（小时）或开镜视场角；确认前不参与任何计算 |
| `(0)` | 同一分钟内的序号 | 去重键的一部分 |

四元数换算式（Unity 约定，与本项目第 2 节完全一致）：

```text
heading = atan2(2(wy + xz), 1 - 2(y² + x²))    // 0° = +Z（正北），顺时针为正
pitch   = asin(2(wx - yz))
roll    = atan2(2(wz + xy), 1 - 2(y² + z²))
```

样本代入结果：`heading ≈ 66.63°`、`pitch ≈ 3.20°`、`roll ≈ 0°`。
交叉验证：`sin(66.63° / 2) = 0.549`、`cos(66.63° / 2) = 0.835`，与文件中的
`y`、`w` 两个分量吻合，说明四元数分量顺序确实是 `(x, y, z, w)`。

采集流程（桌面端，Windows）：

```text
游戏内按截图键
   → 截图写入 %USERPROFILE%\Documents\Escape from Tarkov\Screenshots
   → 监听目录中的新增文件（只匹配文件名，不读取图片）
   → 解析 position 与 heading
   → player.update（source: "screenshot"）→ 服务端广播给队友
```

处理要求：

1. **只读**：只读文件名与文件时间；不读图片内容、不修改、不删除截图。
2. **不回溯**：启动时先记录已有文件，只处理启动之后新增的文件。
3. **去重**：以完整文件名为键；因时间只到分钟，必须结合序号与文件修改时间区分。
4. **节流**：连拍时在默认 2 秒窗口内合并，只上报最后一次。
5. **降级**：解析失败（游戏更新改了格式）时回退到地图点选，并记录一条警告，不阻断上报。
6. **地图归属**：文件名不含地图名，需要由当前 Raid 的地图（日志解析或手动选择）补全。

待确认项：`15.72` 的语义。判定方法——连拍两张（一张腰射、一张开镜）：若数值随开镜变化即为
视场角；若在局内随时间单调增加，则为游戏内时间。

## 9. 必须覆盖的测试用例

1. **往返一致性**：随机 1000 个世界坐标 → 像素 → 世界坐标，误差 ≤ 0.5 米。
2. **控制点自洽**：4 个控制点代入变换后误差 ≤ 0.01 像素。
3. **验证点精度**：额外验证点误差 ≤ 2 像素。
4. **退化输入**：共线/重复控制点抛出明确错误。
5. **视图变换**：缩放锚点不漂移；缩放后再平移结果与解析解一致。
6. **边界**：地图四角与越界坐标不产生 `NaN` / `Infinity`。
7. **截图文件名解析**：真实样本字段、四元数换算、格式容错（缺秒/缺序号/缺扩展名）、
   非法输入与时间越界——见 `packages/shared/tests/screenshot-filename.test.ts`。
